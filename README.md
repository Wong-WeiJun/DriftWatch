# DriftWatch

> Automated cloud infrastructure drift detection for AWS + Terraform

DriftWatch continuously compares live AWS resources against your Terraform state, surfacing configuration drift within minutes via an interactive dashboard and email alerts. Perfect for platform teams that need visibility into when engineers make manual console changes.

---

## The Problem

In teams using Terraform, engineers sometimes make hotfixes directly in the AWS Console. Without drift detection, these changes silently diverge from Infrastructure as Code over time — leading to:

- **Broken deploys** — `terraform apply` fails because the live state has changed
- **Security regressions** — unauthorized ingress rules, public S3 buckets, overly-permissive IAM roles
- **Compliance issues** — audits require that all infrastructure is managed through code

DriftWatch closes this visibility gap.

## How It Works

```
┌─────────────────┐     ┌──────────────────┐     ┌─────────────────┐
│  GitHub Actions │────▶│   ALB / ECS      │────▶│   DynamoDB      │
│  (scan every 6h)│     │   (FastAPI)      │     │   (drift store) │
└─────────────────┘     └────────┬─────────┘     └─────────────────┘
                                 │
                      ┌──────────┼──────────┐
                      ▼          ▼          ▼
                 ┌────────┐ ┌────────┐ ┌───────┐
                 │   S3   │ │ SNS    │ │ boto3 │
                 │(tfstate│ │(email) │ │(AWS)  │
                 └────────┘ └────────┘ └───────┘
```

1. **Trigger** — A GitHub Actions cron job calls `/api/v1/scan/trigger` every 6 hours (or on demand)
2. **Fetch** — The FastAPI backend pulls Terraform state from S3 and live AWS resource state via `boto3`
3. **Compare** — The drift engine diffs expected vs. actual values for each resource
4. **Persist** — Drift events are stored in DynamoDB; high-severity items trigger SNS email alerts
5. **Visualize** — A real-time dashboard renders the latest drift events, filterable by resource type and severity

## Detected Resource Types

| Resource | Attributes Monitored |
|---|---|
| **EC2** | `instance_type`, AMI, subnet, key pair |
| **Security Groups** | ingress/egress rule counts |
| **S3** | versioning, public access block settings |
| **IAM Roles** | path, max session duration |
| **RDS** | instance class, engine version, multi-AZ, deletion protection |

Severity is auto-assigned: **high** for critical attributes like `instance_type`, `publicly_accessible`, or IAM rule counts; **medium** for everything else.

## API Endpoints

| Endpoint | Method | Description |
|---|---|---|
| `/health` | GET | Health check |
| `/api/v1/scan/trigger` | POST | Trigger a drift scan (`dry_run` or full) |
| `/api/v1/drifts/events` | GET | List drift events (filter by `scan_id`, `limit`) |
| `/api/v1/drifts/scans` | GET | List scan summaries |
| `/api/v1/drifts/scans/{id}` | GET | Get single scan result |

Interactive API docs are auto-generated by FastAPI at `/docs` (Swagger UI).

## Local Development

### Prerequisites

- Docker & Docker Compose
- (Optional) Python 3.13 for running tests natively

### Quick Start

```bash
git clone https://github.com/<your-username>/driftwatch.git
cd driftwatch

# Start everything — LocalStack, DynamoDB init, S3 init, FastAPI
docker compose up --build
```

| Service | URL |
|---|---|
| Dashboard | http://localhost:8000/ |
| API Docs (Swagger) | http://localhost:8000/docs |
| Health Check | http://localhost:8000/health |
| LocalStack | http://localhost:4566 |

The compose stack spins up:
- **LocalStack** with DynamoDB, S3, SNS, EC2, and IAM mocks
- **One-shot init containers** that create the DynamoDB table and seed mock AWS resources + a Terraform state file
- **FastAPI app** with hot-reload from your local `backend/` and `frontend/` directories

### Running Tests

```bash
cd backend
pip install -r requirements-dev.txt
pytest tests/ -v --cov=app --cov=models --cov-report=term-missing
```

### Trigger a Local Scan

```bash
# Dry-run (returns immediately, nothing saved)
curl -X POST http://localhost:8000/api/v1/scan/trigger \
  -H "Content-Type: application/json" \
  -d '{"dry_run": true}'

# Full scan (queued background task, results persisted to DynamoDB)
curl -X POST http://localhost:8000/api/v1/scan/trigger \
  -H "Content-Type: application/json" \
  -d '{"dry_run": false}'
```

### Configuration

Copy `.env.example` to `.env` (or set env vars directly):

```bash
AWS_REGION=ap-southeast-2
TF_STATE_BUCKET=driftwatch-state
TF_STATE_KEY=terraform.tfstate
DYNAMODB_TABLE_NAME=driftwatch
SNS_TOPIC_ARN=arn:aws:sns:ap-southeast-2:123456789012:driftwatch-alerts
AWS_ENDPOINT_URL=http://localhost:4566  # only for LocalStack
```

## CI/CD Pipeline

All workflows use **GitHub OIDC** to assume an AWS IAM role — no static AWS access keys are stored in repository secrets.

### `ci.yml` — Pull Request & Main Branch

| Job | What it does |
|---|---|
| **Lint** | `ruff check` + `ruff format --check` on `app/`, `models/`, `tests/` |
| **Test** | `pytest` with coverage → uploads to Codecov |
| **Docker Build** | Builds the image and verifies `/health` responds |

### `deploy.yml` — Production Deployment

Triggered on pushes to `main` that touch backend code.

| Step | Tool |
|---|---|
| Build & Push | Docker Buildx + Amazon ECR |
| Register Task Definition | AWS ECS |
| Deploy Service | `aws ecs update-service --force-new-deployment` |
| Verify | Waits for `services-stable`, then `curl /health` |

### `drift-scan.yml` — Scheduled Scanning

| Trigger | Behavior |
|---|---|
| `cron: 0 */6 * * *` | Full scan (persists results) |
| Manual `workflow_dispatch` | Defaults to `dry_run`, supports filtered resource types |

The workflow polls the API until the scan completes, then reports drift counts in the GitHub Actions log.

## Deployment (Production)

### 1. Bootstrap Infrastructure

```bash
cd infrastructure
terraform init
terraform plan -var-file="terraform.tfvars"
terraform apply -var-file="terraform.tfvars"
```

This provisions:
- VPC with public and private subnets across 2 AZs
- ECS Fargate cluster running the DriftWatch container
- Application Load Balancer (public-facing)
- DynamoDB table, S3 state bucket, SNS topic

### 2. Push the First Image

The `deploy.yml` workflow handles this automatically on push to `main`, or:

```bash
aws ecr get-login-password | docker login --username AWS --password-stdin <account>.dkr.ecr.<region>.amazonaws.com
docker build -t driftwatch .
docker tag driftwatch:latest <account>.dkr.ecr.<region>.amazonaws.com/driftwatch-development:latest
docker push <account>.dkr.ecr.<region>.amazonaws.com/driftwatch-development:latest
```

### 3. Configure GitHub Actions Secrets

| Secret / Variable | Value |
|---|---|
| `AWS_ROLE_ARN` | IAM role ARN from `github_actions.tf` output |
| `API_URL` | ALB DNS name (e.g. `https://driftwatch-alb-xxx.ap-southeast-2.elb.amazonaws.com`) |

## Key Design Decisions

### Why ECS Fargate over Lambda?

Scans span 5 resource types and can take 10–30 seconds in large accounts. While Lambda could work, Fargate is more appropriate for a stateful API server that serves the dashboard and handles background tasks.

### Why DynamoDB over RDS?

Drift events are append-only with no relational queries. DynamoDB's `PAY_PER_REQUEST` billing means near-zero cost for infrequent scans, with no connection pool management.

### Why Stateless Scan Engine?

The engine pulls fresh state from S3 and boto3 on every run — no cached state to go stale. This allows horizontal scaling without coordination concerns.

### Why Vanilla JS for the Frontend?

The dashboard is intentionally lightweight (a single `index.html` file). It loads in milliseconds, requires no build step, and is trivial to embed into the FastAPI static file server.

## Architecture Decisions at a Glance

| Decision | Choice | Rationale |
|---|---|---|
| Auth | GitHub OIDC | No long-lived credentials in repo secrets |
| State storage | S3 + DynamoDB | Serverless, ops-free, high availability |
| Alerts | SNS + email | Simple, reliable, no external service dependency |
| Scheduling | GitHub Actions cron | Zero infrastructure cost, audit trail built-in |
| Testing | pytest + moto | Fast unit tests with mocked AWS services |
